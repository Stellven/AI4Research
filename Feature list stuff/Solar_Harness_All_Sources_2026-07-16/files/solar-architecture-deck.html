Solar.
An AI-Native Operator Runtime

It compiles user intent into logical operators, binds them to physical AI operators, schedules them as DAGs, and verifies outputs through evidence gates.

把自然语言当控制面，把需求当可编译 Artifact，把AI 产品当物理算子，把外部能力当可调度 Capsule，把工程任务当带证据门禁的 DAG 执行。

Solar Harness is not a wrapper over LLM APIs. It is a scheduler over heterogeneous AI execution surfaces.
Solar Harness 不是 LLM API 的封装器，而是异构 AI 执行面的调度器。

What Is Solar01 / 18

Solar 自上而下由六层构成：用户接入 → Harness → Core → Knowledge → Data Foundation → 外部模型算子
核心不是封装一个模型，而是把多种 AI 入口与执行面建模为可调度算子

逻辑算子描述"做什么"（需求编译 / 代码实现 / 浏览器研究 / Deep Research / 评审 / 测试 / 知识沉淀 / 自优化）；物理算子描述"谁、在哪、用什么套餐/模型/工具做"。Harness 由此成为 AI-native execution fabric。

架构定义

prompt 集合 普通聊天助手 多开 Agent 的 demo 只做 RAG 的知识库
核心结论
  1. 六层自上而下：用户接入 → Harness 控制面 → Core → Knowledge → Data Foundation → 外部模型算子。
  2. 所有入口(cmux/OpenClaw/Codex/Claude Code…)都先汇入 Harness——唯一最高调度者，不直接驱动底层。
  3. 外部大模型服务被封装为物理/逻辑算子(暴露 features/skills/MCP/tools)，由 Harness 按成本·能力·风险·证据选路调度。

Requirement Compiler03 / 18

需求不直接执行，而是像编译器一样逐级收敛为可验证的 IR；
而编译过程本身也是可自优化的（GEPA optimize_anything）

传统 Agent 把 prompt 直接交给 Planner；Solar 先把需求编译成可审查、可调度、可约束、可定位失败阶段的 IR。更进一步：把编译器各阶段当作可评估的 text artifact，由 GEPA 自优化——数据底座提供评估所需的真实证据。优化回路与底座反馈为规划实现。

FIG 03 · 编译管线（左）+ GEPA 自优化回路（右上，规划）+ 数据底座作为评估证据源（右下）
  • 编译的好处：需求不再只活在对话里——边界可审查、依赖可调度、写入范围可约束、验收可执行、失败可定位到具体阶段。
  • 编译过程可自优化（规划）：把 contract/PRD/plan/TaskGraph 生成策略当作 text artifact，由 GEPA 用 (score, side_info) + Pareto 迭代，经人审 Promotion Gate 回填——需求编译质量随真实任务持续变好。
  • 数据底座的价值：evaluator 不是空打分——ConceptGraph 校验语义 grounding、Code/DatasetGraph 核对权威源与真实逻辑、Trace/MemoryGraph 提供历史失败模式与可复现、PolicyGraph 校验边界审批。没有底座，自优化就退化成黑盒搜索。
  • epic_decomposer.py / contract-template-v2：大需求拆为 epic + bounded child + parent DAG，交付前必出 plan.md 与 task_graph.json。

核心结论
  1. 把需求当作编译对象，而非直接执行的指令——与普通 Agent 的第一道分水岭。
  2. 再进一步把编译器本身当作可优化对象（GEPA optimize_anything）：需求编译质量可随真实任务自演进（规划实现）。
  3. 这条自优化回路的含金量来自数据底座——它提供 grounding、权威逻辑、历史失败与策略边界等可行动证据，让 evaluator 给出真梯度而非黑盒分数。
Logical ⟂ Physical Operators04 / 18

AI 时代的执行资源不再同质：先定义逻辑算子，
再在运行时绑定物理算子，为调度保留选择空间

同一逻辑任务（实现功能 / 做研究 / 评审改动）可由 API 模型、Claude Code、Codex、Web 版 GPT/Gemini/DeepSeek、远端 Worker 或本地模型执行——价格、能力、上下文、工具链、并发与可靠性差异巨大。

FIG 04 · 逻辑算子（稳定）⟂ 物理算子（异构执行面）的运行时绑定
  • 原因 1 · 成本结构不同：套餐型 Web/TUI 算子在长任务、交互式代码、文件/浏览器任务上可能显著低于 API 路径。
  • 原因 2 · Web 版能力更完整：Web 产品常更早集成浏览器、文件、代码解释器、多模态、长上下文、项目工作区。
  • 原因 3 · Code Agent 本身就是多 Agent Runtime：Claude Code / Codex 内部已具备计划、工具调用、文件编辑、测试、子任务并行。
  • Solar 不替代 Claude Code / Codex 的内部智能——把每个实例封装成物理算子，并在外层加调度、证据与优化控制面。
核心结论
  1. "做什么"与"谁来做"解耦，执行计划可按成本/能力/风险/证据动态选择。
  2. Code Agent 被当作带内部 agentic runtime 的物理算子，不被降级成普通 LLM call。
  3. 调度器该问的不是"哪个模型最强"，而是"在此预算/风险/证据要求下哪个执行面最合适"。

关于成本（稳健措辞）

在许多实际工作负载中，订阅套餐与 Web 端能力相对 API 调用存在明显成本优势；某些长期工程任务通过套餐型 Web/TUI 算子执行，单位成本可比纯 API 路径低一个数量级以上。Solar 把这种差异作为系统调度的资源模型，而非临时技巧——后续以 benchmark 报告给出更精确的成本曲线。

核心结论
  1. 这是 AI Compute Acquisition Strategy，不是"薅羊毛"：把异构资源纳入统一调度 + 证据闭环。
  2. 目标不是盲选"最强模型"，而是在质量 / 成本 / 延迟 / 稳定性 / 证据可得性间做调度。
  3. 现行调度基于 multi-task TUI pane 无头执行：多 node 并行绑定异构模型，静态 main/lab 名单已废弃。

Parallel Operator Scheduling07 / 18

复杂系统开发的瓶颈不是"单模型够不够聪明"，
而是任务能否安全并行、失败隔离、结果合并、证据闭环

FIG 07 · 三层并行 + 并行前提（graph_scheduler / pane_lease）

  • graph_scheduler.py 四条源码硬保证：① 无效 DAG 快速失败（缺依赖/环/重复节点）；② ready 节点要求依赖全 PASS；③ 写域重叠的节点永不共享批次；④ 未声明写域者按独占写者处理。
  • pane_lease.py 把 pane 分为 no_pane / busy / dead 三态，用 dispatch_id 与 TTL 做 acquire/release/reap。写域冲突判定采用路径前缀重叠算法。

Context Map Plane · PEEK12 / 18

长期任务最大的浪费是 orientation tax：
Context Map 是某个外部上下文的语义地形图

它不是 RAG、不是聊天历史、不是普通 memory——保存的是 active external-context state，而非过去对话、原始材料或任务策略。

FIG 12 · RAG = 证据访问；Context Map = 语义导航状态
  • 面对同一代码仓 / 文档库 / 研究主题，反复工作的最大浪费就是每次都要重新理解上下文：结构在哪、哪些实体重要、哪些路径不能动。
  • Context Map 把这种 orientation knowledge 变成可维护、可更新、可淘汰、可复用的运行态状态。
  • 保存：roadmap · key entities · domain constants · reusable results · parsing schema · open questions · contradictions · evidence refs · staleness。
  • 与 RAG / Shared Chat / Prompt Learning 的根本区别：保存当前外部上下文状态，不是历史、原料或策略。
核心结论
  1. 长期 Agent 的隐性成本是 orientation tax，Context Map 直接消除它。
  2. 它是一种新的运行态状态，介于 RAG 与 memory 之间但都不是。
  3. "导航"而非"检索"——回答世界如何组织，而非证据在哪。

Agent JIT · 编译执行— 前沿吸收 II

从"边想边点"到"先编译、验证、调度、再执行"
Agent latency 第一杀手不是浏览器慢，是每步问模型

Agent JIT（Latency-Optimizing Web Agent）把自然语言任务在执行前编译成低层代码计划：工具调用 + 少量 LLM 调用 + 控制流 + 并行策略，多候选静态验证后选成本最低者。Browser-Use 有 73% latency 花在 LLM calls 上——可确定步骤本不必问模型。

FIG · Agent compiler stack：ABI → IR/CFG → cost → scheduler → 执行
实测（37 任务 · 5 应用）
  • 平均 latency 10.9s vs 118.5s（≈10.4×）；准确率 93% vs 65%。
  • Tool Protocol 把 ordering violation 从 59% → 25%，有效计划率 79%→96%。
与 Capsule / Solar 对位
  • pre/post state invariant = tool protocol；Capsule ABI 是它的企业版（+权限/副作用/回滚/成本/失效规则）。
  • 三层 runtime：Interpreter（探索）/ Compiled（熟悉应用）/ Adaptive（生产：编译+验证+动态调度+fallback+重编译）。
  • Deep Research 也该 JIT：并行搜独立子主题、hedge 高不确定来源、稳定流程固化为 skill。

保留：适合重复访问的应用（offline setup 可摊销），非全网通吃；UI staleness / stochastic env / 安全副作用是硬问题，需 invalidation + fallback + sandbox。

核心结论
  1. Agent 从解释器 → 编译器 + runtime：自然语言=源码 · 工具协议=ABI · pre/post=类型+状态系统 · CFG=IR · cost=optimizer · serial/parallel/hedge=scheduler。
  2. 三篇合一(PEEK 上下文地图 · optimize_anything 自优化 · Agent JIT 编译)构成下一代 Agent OS 骨架：L1 Orientation → L2 Tool ABI → L3 Plan IR → L4 Scheduler → L5 Optimizer → L6 Capsule。
  3. 对 Solar：新增 Agent Compile Operator，与 Capsule ABI、GEPA 优化器、Runtime Transcript 闭环咬合。

12 Design Principles— 设计哲学 II

十二条设计原则：每一条都对应一处架构决策

01 · Control Surface
Natural language is the high-level API of the control plane.
自然语言不是聊天内容，而是系统控制面的高层 API。
02 · Compilable Requirements
Requirements are compilable artifacts, not prompts.
需求可编译为 Contract / PRD / TaskGraph IR，而非临时 prompt。
03 · Unit of Execution
Models are not the unit of execution; AI-capable environments are.
模型不是执行单位；具备 AI 能力的执行环境才是。
04 · Logical ⟂ Physical
Logical operators define what; physical operators define who/where/with-what.
逻辑算子定义做什么，物理算子定义谁来做、在哪、用什么做。
05 · First-Class Browser/TUI
Browser, Web AI, Code Agent panes are first-class operators, not hacks.
浏览器、Web AI、Code Agent pane 都是一等物理算子。
06 · Fleet Scheduling
Subscription-era AI requires scheduling the whole fleet.
算力来自 API/订阅/Web/Code Agent/本地/远端，须调度整个舰队。
07 · Bounded Parallelism
Parallelism requires dependency, write-scope, lease, capability and evidence boundaries.
并行不是多开 Agent，而是在边界约束下释放吞吐。
08 · Schedulable Capabilities
Capabilities are schedulable assets, not plugins.
Skill / MCP / Web 功能建模为可调度、可评估的 Capability Capsule。
09 · Evidence = Completion
No handoff, eval, log, verifier and gate — no completion.
没有证据协议，就不能宣称完成。
10 · Context as State
Context is runtime state, not chat history or raw RAG.
上下文是可维护的 Context Map / Evidence Index / Experience Memory。
11 · Evaluator-Driven Opt
Self-optimization needs evaluators, not reflection.
自优化 = artifact + evaluator + side_info + Pareto + promotion gate。
12 · Guardrails as Semantics
Guardrails must become runtime semantics, not prompt text.
边界进入 workflow/architecture guard、write_scope、permission、evaluator。
核心结论
  1. 这 12 条不是口号，每条都落到具体模块（epic_decomposer / graph_scheduler / research/evaluator / workflow_guard …）。
  2. 贯穿主线：需求 → 算子 → 并行 → 证据 → 上下文 → 优化，对应控制/执行/状态/优化四个面。
  3. 最短表达：让 AI 工作像系统软件一样运行。
Closing Statement

Solar 不是围绕单个模型、单个界面或单个 Agent 循环构建的——它是 AI 时代的 execution fabric。

它把自然语言视为控制面，把需求视为可编译 Artifact，把 AI 产品视为物理算子，把外部能力视为可调度 Capsule，把工程任务视为带证据门禁的 DAG 执行。在同一控制面下编排模型舰队、Code Agent、浏览器原生算子、本地与远端 Worker，以及可自优化的策略系统。

Solar Harness is not a wrapper over LLM APIs. It is a scheduler over heterogeneous AI execution surfaces — an AI-native runtime that orchestrates model fleets, code agents, browser-native operators, local and remote workers, and self-optimizing policies under one control plane.

Solar makes AI work run like system software: compiled, scheduled, bounded, evidenced, and optimized.
